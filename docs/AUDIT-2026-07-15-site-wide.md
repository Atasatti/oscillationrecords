- [ ] **V01 · HIGH — S3 bucket is public-read; sensitive DAM assets (masters, stems, EPKs, contracts/documents) have no server-side authorization — only the key UUID protects them**
  - **Where:** `lib/s3.ts:43` · **Dimension:** security · **Category:** data-exposure
  - **What:** The canonical stored URL for every uploaded file is the raw public object URL publicFileUrl() = https://<bucket>.s3.<region>.amazonaws.com/<key> (lib/s3.ts lines 43-45). The admin Assets UI renders and opens these directly — <img src={a.fileUrl}> (AssetsClient.tsx line 450), <a href={a.fileUrl} target="_blank"> 'Open' (line 457/493), and bulkDownload sets el.href = a.fileUrl (line 251) — and the competition page hardcodes a raw S3 GET (BenertRemixPageContent.tsx line 116). Those only work if the objects are public-read, indicating the whole bucket is world-readable. DAM asset keys are assets/{category}/{uuid}/{basename} (app/api/assets/presign/route.ts line 35) and the categories include master, stems, epk and document (lib/asset.ts lines 7-9) — i.e. unreleased masters and legal/contract documents. There is no S3-side authorization on these objects; the sole confidentiality control is the 122-bit crypto.randomUUID in the path. The catalog:read-gated download shim (app/api/assets/download) only adds a Content-Disposition filename — it does not restrict access, since the object is already public.
  - **Impact:** Any sensitive asset URL that leaks — via a DB dump, application/proxy logs, a copied 'Open' link, browser history, or an accidentally shared file — becomes permanently world-readable with no revocation short of deleting/re-keying the object. Unreleased masters, stems and contracts stored in the DAM are exposed to anyone who ever obtains the URL.
  - **Suggested fix:** Serve the sensitive assets/ prefix from a private bucket/path and require per-request presigned GETs (the download shim already presigns — drop the public fileUrl for these). If the public site needs some media public, split public (covers/press) from private (masters/stems/documents) prefixes with a bucket policy that blocks public reads on the private prefix.

- [x] **V03 · MEDIUM — Unescaped, unbounded user input compiled into a MongoDB $regex (ReDoS) in newsletter subscriber search** — ✅ FIXED: `q` is now length-capped (64) and regex-escaped before `contains`, so it's a literal substring match (no ReDoS / regex injection). Verified live: normal search still returns results; `(a+)+$` now matches literally (0 results, fast, no hang).
  - **Where:** `app/api/admin/newsletter/subscribers/route.ts:29` · **Dimension:** security · **Category:** nosql-injection
  - **What:** The subscriber search takes the raw `q` query param (line 28: `const q = (searchParams.get("q") || "").trim();` — no length cap, no sanitisation) and passes it straight into a Prisma string filter: `const where = q ? { email: { contains: q, mode: "insensitive" as const } } : {};`. On the MongoDB connector, Prisma's `contains`/`mode:"insensitive"` compiles to an unanchored `{ email: { $regex: <q>, $options: 'i' } }` and does NOT escape regex metacharacters, so `q` is interpreted as a regular expression by the database. This `where` is then executed on three paths — the CSV export `findMany` (line 32, over ALL matches), the paginated `findMany` (line 52), and `count` (line 59). This is the only place in the codebase where client input reaches a DB regex (verified: no other `mode:"insensitive"`, no `$regex`/`new RegExp`; every other search — releases, artists, press, outreach contacts — filters in JS with length-capped `fuzzyScore`/`includes`, so they are not affected).
  - **Impact:** An authenticated user holding only the low-privilege `outreach:read` role can send a catastrophic-backtracking pattern (e.g. `q=(.*a){30}b` or `q=(a+)+$`), forcing an unanchored, case-insensitive regex collection scan whose evaluation backtracks exponentially per document — pinning a database CPU core and degrading/hanging the shared MongoDB instance (denial of service). The absence of a length cap on `q` (the public search routes deliberately `.slice(0,64)`) lets the attacker supply an arbitrarily long pattern to worsen it. A read-only staff role should not be able to impact database availability.
  - **Suggested fix:** Do not feed raw user input to `contains`. Either (a) length-cap and escape regex metacharacters before use (e.g. `q.slice(0,64).replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`), or (b) filter in JS after an indexed fetch as the other admin search endpoints do (lib/admin-data.ts `fuzzyScore`), or (c) if only exact/prefix matching is needed, use `equals`/`startsWith` on the indexed field. Add a length cap on `q` regardless.
  - **Verification (high confidence):** Confirmed real, not a false positive. app/api/admin/newsletter/subscribers/route.ts:28-29 takes the raw `q` query param (trimmed only, no length cap, no sanitization) and puts it into `{ email: { contains: q, mode: "insensitive" as const } }`, used unchanged in three query executions: the unbounded CSV findMany (:32-36, no `take`), the paginated findMany (:52-58), and count (:59, run concurrently with findMany via Promise.all). Verified via external research (Prisma GitHub issue #18803, corroborated by #18564/#14663) that Prisma's MongoDB connector does NOT escape regex metacharacters for contains/mode:"insensitive" — it forwards the string directly into a MongoDB $regex filter — and this is a longstanding, still-open behavior applicable to the pinned @prisma/client@^6.19.3. MongoDB's $regex uses a PCRE backtracking engine, so classic catastrophic-backtracking patterns (e.g. (a+)+$) are effective against it, and since contains is unanchored, no index can be used (forces a COLLSCAN) regardless of the @unique index on email. Reachability confirmed: requirePermission(request, "outreach:read") properly gates the route (no bypass found), but lib/permissions.ts:73 grants outreach:read to the `viewer` role, documented as "View the whole admin — catalog, outreach and analytics. Change nothing." — literally the app's lowest-trust staff tier, plus the `promotion` role (:71). Comparator routes (app/api/releases/route.ts, app/api/artists/route.ts) use length-capped JS-side fuzzy filtering, confirming this route is a genuine outlier rather than an accepted pattern. No compensating controls exist: grep confirms no length cap on q (unlike sibling routes), no rate limiting on this route (lib/rate-limit.ts is wired into contact/releases/artists/upload/analytics routes but not here), zero maxTimeMS anywhere in the repo (no server-side query timeout), and no Prisma $use/$extends middleware to sanitize input. lib/prisma.ts uses one global PrismaClient singleton with maxPoolSize:10 shared by the whole app and only a client-side socketTimeoutMS:60000 (doesn't abort the op server-side) — since a single plain request already fires two concurrent expensive regex scans (findMany+count), a modest number of concurrent malicious requests could exhaust the shared pool and degrade unrelated site routes, a larger blast radius than the single endpoint. Severity adjusted from low to medium: trivially exploitable (one crafted GET, textbook evil-regex patterns) and reachable by the app's explicitly lowest-trust "change nothing" role with zero layered defenses (where sibling code has at least one), which undersells "low." Not "high" because it requires authenticated internal/staff access (not anonymous-internet-reachable), is availability-only (no confidentiality/integrity impact), and is operationally recoverable (kill the op, ship a one-line escape/cap fix).
