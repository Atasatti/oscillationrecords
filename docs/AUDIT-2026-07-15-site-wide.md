## Executive summary

The Oscillation Records codebase is a well-structured, actively-maintained Next.js 15 / Prisma / MongoDB app in generally good health: this audit surfaced no critical or remotely-exploitable vulnerabilities and no data-loss bugs, and several issues had already been fixed mid-audit. The most urgent items are five high-severity findings — a public-read S3 bucket that leaves unreleased masters and legal contracts protected only by a UUID (any leaked URL is permanently world-readable); a /contact page unusable on mobile, which is the site's primary demo/contact conversion surface; release dates rendering a day early with React hydration errors across every release page and the homepage for all Americas visitors; newsletter campaigns that can become permanently stuck in "sending" with no in-app recovery; and a keyboard-inoperable "Meet the Artists" carousel (WCAG Level A). Beneath those, the medium tier is dominated by systemic themes rather than one-offs: a stateless-JWT session layer that is neither revocation-aware nor carries a usable user id, under-constrained/public object storage, a pervasive "fetch everything and aggregate in JS" database pattern (harmless at today's tiny data volumes but linear-growth), optimistic admin UIs that silently diverge from the server, and recurring accessibility and image-optimization gaps. Encouragingly, for nearly every finding the correct pattern already exists elsewhere in the tree (timeZone-pinned dates, semantic &lt;button&gt; carousels, next/image, DB-side filters, transaction-wrapped writes, resolveUserId()), so most remediation is small, low-risk consistency work rather than new engineering. Fix the five highs first, then address the session/identity and object-storage themes, which carry the broadest security and correctness leverage.

## Cross-cutting themes

- Session/identity layer is neither revocation-aware nor identity-correct: edge middleware gates admin pages on a 30-day JWT role with no DB recheck (demoted staff still read PII on direct-DB-read server components), and session.user.id/token.sub carries the Google OAuth subject instead of the Mongo user id, breaking @-mention reminders, 'My tasks' filters and other identity/ownership lookups (app/admin/*/page.tsx, lib/auth.ts, app/api/outreach/mentions).
- Object storage is under-secured: five presign routes sign PUTs with no size limit and no key-prefix confinement, and the canonical asset URL is a public-read S3 object protected only by a UUID, so sensitive DAM assets (masters, stems, contracts) have no server-side authorization and uploads can be abused for cost inflation or cross-scope overwrite (lib/s3.ts, app/api/upload/*).
- Database access scales with data, not results: the analytics dashboard and per-content routes, songs/latest, outreach/contacts and the audit-log dropdown fetch unbounded/whole-table row sets and aggregate in Node, and has/hasSome artist-id filters run full-collection scans for lack of multikey indexes — cheap at today's tiny volumes but linear-growth risk (app/api/analytics/*, app/api/admin/audit, prisma/schema.prisma).
- Optimistic admin mutations don't reconcile with the server on success, so the UI silently diverges from actual DB state: recurring-task completion hides the spawned next occurrence, and asset bulk-delete removes rows (and toasts success) even when the delete failed (app/admin/tasks/page.tsx, app/admin/assets/AssetsClient.tsx).
- Multi-step write paths lack atomicity/recovery: release track writes happen outside the transaction (partial tracklist / duplicate tracks), newsletter send has no try/catch around post-claim work (campaign stuck in 'sending' forever), and pitch status sync commits the pitch before an unverified contact update (app/api/releases/[releaseId], lib/newsletter-send.ts, app/api/outreach/pitches).
- Media/LCP performance: public and admin surfaces render raw unoptimized <img> of full-resolution S3 originals (with eslint no-img-element disabled) instead of next/image, don't mark LCP images priority, and hide first-viewport content behind an opacity:0 reveal until hydration (components/local-ui/PressCard.tsx, app/admin/assets/AssetsClient.tsx, components/local-ui/ScrollReveal3D.tsx, MeetArtistSection.tsx).
- Accessibility gaps recur, several at WCAG Level A: carousel controls built as <div onClick> with no keyboard/AT semantics, form fields with no programmatic label, interactive <button>s nested inside a card <Link>, sub-AA contrast on the sitewide player, and aria-label on role-less spans (MeetArtistSection.tsx, ReleaseDetailsPanel.tsx, ArtistCard.tsx, MusicPlayer.tsx, ExplicitBadge.tsx).
- Next.js metadata merges shallowly, so partial per-page openGraph/twitter overrides silently drop inherited images/titles: og:image is lost on five marketing pages and owned press posts fall back to a generic X card (app/(main)/*/page.tsx, app/(main)/press/[slug]/page.tsx).
- Fixes are mostly consistency work, not new engineering: for nearly every finding the correct pattern already exists in a sibling (timeZone-pinned dates, visibility-filtered artists, semantic <button> carousels, next/image, transaction-wrapped writes, resolveUserId()), and a small cluster of code-hygiene debt in security-adjacent code (auth-guard preamble copy-pasted x4, a dead revocation-blind admin helper, an `as never` cast disabling type checks) raises latent-bug/drift risk.

- [x] **#3 · HIGH — Release dates render one day early (+ hydration mismatch) in client components: toLocaleDateString without timeZone**
  - **Where:** `app/(main)/releases/[releaseId]/ReleaseDetailView.tsx:343` · correctness
  - ✅ **Fixed + verified in-browser 2026-07-15** (commit `d0e714d`): added `timeZone:"UTC"` to ReleaseDetailView (×2), UpcomingReleasesSection, and PressCard. Probe confirmed a midnight-UTC date renders "August 14" (LA, pre-fix) vs "August 15" (post-fix); ahead-of-UTC zones unchanged.
  - **What:** Release dates are stored as midnight-UTC DateTime values and serialized to ISO strings (catalog-data.ts: `releaseDate.toISOString()`). - [x] **#4 · HIGH — Newsletter campaign can get permanently stuck in "sending" (unrecoverable)** — ✅ Fixed 2026-07-16 (`24934d4`): try/catch resets to "failed"; claim re-admits a stale "sending" row past 15m.
  - **Where:** `lib/newsletter-send.ts:33` · correctness
  - **What:** sendCampaignNow() atomically claims a campaign by moving draft/scheduled/failed -> "sending" (updateMany, lines 29-33), then loads subscribers and sends in batches, and only writes the final status at the very end (lines 53-56). The work between the claim and the final update is NOT wrapped in try/catch, and the batched sequential loop (10 recipients/batch, each sendEmail with a 15s AbortSignal.timeout) can exceed the serverless function's max duration. - [ ] **#7 · MEDIUM — Role revocation is not enforced on server-rendered admin pages that read the DB directly (PII exposure to just-demoted staff)**
  - **Where:** `app/admin/newsletter/subscribers/page.tsx:13` · security
  - **What:** Several admin pages are React Server Components that query sensitive data directly via Prisma with NO auth call in the render path. app/admin/newsletter/subscribers/page.tsx:16-23 reads subscriber emails, and app/admin/messages/page.tsx:18-38 reads up to 500 contact messages (names, emails, message bodies) — both shipped in the initial HTML. Their only gate is the edge middleware (middleware.ts:123-133), which is purely token-level: getAuthToken decodes the JWT and isStaffToken/tokenCan check token.role with NO database read. The admin layout (app/admin/layout.tsx) performs no server-side guard either. - [ ] **#10 · MEDIUM — Slug collisions resolve non-deterministically: duplicate release/artist/press titles make one URL shadow the other and serve wrong content**
  - **Where:** `lib/catalog-data.ts:485` · correctness
  - **What:** Slugs are derived from names, and resolution picks the FIRST match from an unordered query. `getReleaseSlugIndex` (lines 470-473) runs `prisma.release.findMany({ where: { status: { not: "DRAFT" } }, select: {...} })` with NO `orderBy`, and `resolveReleaseIdBySlug` (line 486) does `index.find((r) => r.slug === slug)?.id`. Two public releases whose titles slugify identically — common in music (different artists releasing tracks named e.g. "Waves"/"Intro"/"Forever", or a single later re-released on an EP/album with the same title) — collapse to one slug. Whichever release Mongo returns first (natural order, not guaranteed stable across writes/ISR regenerations) wins the slug; the other release is unreachable by its pretty URL and its page serves the WRONG release. Worse, a legacy `/releases/<id>` link to the shadowed release (page.tsx lines 23-27) 308-redirects to `/releases/<slug>`, which then resolves to the OTHER release — so an old bookmark silently lands on the wrong record.   - **Impact:** Two public items whose titles slugify identically collapse to one URL — the other becomes unreachable and its URL serves a different entity's content; legacy /id links 308-redirect to the wrong entity; the sitemap emits duplicate URLs and canonicals collide so Google merges the two (no live occurrence today, but zero validation prevents it).
  - **Fix:** Either add a stored, uniqueness-enforced slug field, or disambiguate on collision (append a short id suffix) and make the index query deterministic (`orderBy: [{ createdAt: 'asc' }]`) so at least the winner is stable. Detect duplicate slugs at build/admin-save time.
